# Dashboard identity and operations

The dashboard reuses ASP.NET Core authentication. Configure authentication in the host, call `AddWorkThroughDashboard`, and mount `MapWorkThroughDashboard` at the chosen path. The standalone sample in `samples/Demo.Dashboard` demonstrates OIDC authorization code with PKCE and a secure, HTTP-only session cookie. User accounts, invitations, MFA, password resets, and role membership belong to the identity provider; WorkThrough does not maintain a second user database.

Set `Identity__Authority`, `Identity__ClientId`, and `Identity__ClientSecret` through the host environment/secret store, register `/signin-oidc` with the provider, and run the host on HTTPS. Persist and protect ASP.NET Data Protection keys across dashboard instances. The sample role mapping is in `appsettings.json`; permissions are added only from validated token roles. No tokens are saved in browser local storage. Sessions expire after 30 minutes; immediate role revocation requires host-specific session validation. No real identity-provider login is claimed verified without configured provider credentials.

Each dashboard operation has a `WorkThrough.<permission>` authorization policy. The default policies require the matching `workthrough.permission` claim. Hosts can replace them after `AddWorkThroughDashboard`; policies receive a `DashboardResource` containing the request path and route values. The initial deployment boundary is one configured store/environment per dashboard. It is not a multi-tenant row-filtering system. Never use correlation IDs as access control.

Metadata access is `executions.read`. Payloads, outputs, progress descriptions, exception messages, and stack traces additionally require `payloads.read`. Administrators do not automatically receive this permission. Separate policies cover retries, cancellations, flow recovery, definition edits/publication/retirement, schedules, limits, and audit reads. The server checks permissions on direct API calls; hiding a button is not authorization.

Administrative POSTs require anti-forgery tokens, a unique command ID, a reason, and the applicable expected attempt/revision. Actor identity comes from trusted server claims (`iss` plus `sub`/NameIdentifier), never the request body. The mutation, command receipt, redacted change summary, and successful audit commit together. Repeating an identical command returns its original result; reusing its ID for different work is rejected. Configure host access/security logging for denied attempts; those are not presented as committed changes. The append-only product API does not prevent a database administrator altering data.

Exception text can contain secrets. Configure `JobWorkerOptions.DescribeFailure` to redact it before storage, apply database access/retention controls, and limit diagnostics permission. Default logs identify failed jobs without dumping their input.

The OIDC sample follows [ASP.NET Core's OIDC web authentication guidance](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-oidc-web-authentication). Development without an authority explicitly enables anonymous access; use that mode only for the isolated local sample.
